9 - Audit Log

A small, append-only, tamper-evident record of what a device decided: who connected, who was refused, who was banned, which pairing windows were opened, which group changes were accepted. One file. It can be opened read-only so someone can look without being able to change it.

Quick use

using var audit = AuditLog.Open("audit.log", key);      // read + append. One writer at a time.
using var recording = audit.Attach(node);                // the node's decisions are written down by themselves
audit.Append("report.opened", subject: "q3.pdf");        // and your own events

using var viewer = AuditLog.OpenReadOnly("audit.log", key);
foreach (var e in viewer.Read(kind: "peer.banned")) Console.WriteLine($"{e.TimeUtc} {e.Subject} {e.Detail}");
var result = viewer.Verify();                            // result.Ok  (or result.BadSeq and result.Problem)

audit.Seal();                                            // done with it: mark the file read-only at the OS level
AuditLog.Unseal("audit.log");                            // a deliberate step to write again

What Attach records

Kind When
peer.connected / peer.disconnected a device's session starts / ends (with its key fingerprint, or why)
device.paired a new device joined with a pairing code
pairing.offered / pairing.cancelled a pairing window was opened / closed by hand
peer.kicked / peer.banned / peer.unbanned this device removed or readmitted someone
handshake.refused a connection attempt was turned away (banned, unknown device, name already paired with other keys)
command.denied a command was refused by CommandAuthorizer
group.introduced / group.revoked this device announced a device to the group / asked to remove one
group.accepted / group.refused this device decided on someone else's announcement (and who made it)
tls.group.joined this device adopted another device's TLS authority while pairing

Anything else: audit.Append("your.kind", subject, detail). A kind is letters, digits, ., _, -.

Refused connections can come from anybody, so repeats of the same (who, why) within a minute are counted into one entry instead of filling the disk.

How it detects tampering

Each entry contains the hash of the entry before it. Change, remove, add, reorder or repeat an entry and the chain breaks from that point; Verify() names the first bad entry.

Without a key With a key (SecureData)
Accidental corruption, clumsy edits Detected Detected
Someone who knows the format rewrites history NOT detected: they recompute every hash Detected: they cannot make valid hashes (each is an HMAC)

So use a key for anything that matters. Keep the key out of the same folder as the log.

What it can NOT see

  • Entries cut off the end, on its own. What remains is still a valid chain. That is what the other devices are for (below), or keep audit.Head yourself and call Verify(expectedHead).
  • Someone who has the key AND the device's own identity, which is the device itself. A signed log (below) can't be forged by anyone else.
  • Deleting the whole file. Reading a missing log is an error, not an empty log.

Read-only, sealing, and safety

  • OpenReadOnly can Read and Verify, cannot Append or Attach, and works while the writer is running.
  • Only one writer can have a log open (a second Open fails).
  • A log that ends in a half-written entry, or whose newest entry fails its check, is refused for writing rather than added to.
  • Seal() closes the writer and sets the file read-only (the attribute, and 0444 on Unix). A sealed log refuses to open for writing and says why. It guards against accidents and casual edits, not against someone with the rights to undo it.
  • Every entry is flushed to disk before Append returns.
  • A failure to write (disk full) never reaches the node: see Failures and the AppendFailed event.

Signed by the device, and kept by other devices

The key stops edits, but whoever holds it can write a whole convincing log, and a chain alone can't see entries cut off the end. Two things fix that.

//on the device that writes: every entry is signed with the device's own private key (Dilithium5)
using var audit = AuditLog.Open("audit.log", key, signer: Me);                  //Me is this device's YuukoIdentity
using var anchor = audit.AnchorTo(node, "main");                               //after every entry, the newest head is sent to the devices we are connected to

//on the devices that watch
using var witness = new AuditWitness(node, "heads.json", FileKey);             //the path and key are optional: without them it is kept in memory

//any time later, on the writer or on whoever reads the file
var result = await audit.VerifyWithWitnessesAsync(node, "main", expectedSigner: Me.Fingerprint);
//result.Ok, result.Problem ("entries were cut off the end", "the log was rewritten"...), result.Witnesses (how many had seen the log)
Call What it does
AuditLog.Open(path, key, signer) Signs every entry. A new log starts with an entry (log.signer) that holds the signer's public keys. Only the same device can carry on writing it
audit.Verify(expectedHead, expectedSigner) With expectedSigner (a fingerprint) every entry has to be signed by that device, so a log forged with the key, or with the signatures taken off, is refused
audit.AnchorTo(node, name) Sends the newest head to every connected device after each entry, and to each one that connects later
new AuditWitness(node, path, key) Remembers the newest head each device told it (encrypted file, saved a few seconds after a change)
audit.VerifyWithWitnessesAsync(node, name, expectedSigner) Verify, then ask the connected devices what they saw

What the others catch:

  • Entries cut off the end: a device saw an entry newer than the last one in the file.
  • A rewritten log: the entry a device saw is not the one in the file at that place (even if the file is now longer), or a device was told two different versions of the same entry.
  • A device that is behind (it saw an older entry that is still in the file) is fine.

Things to know:

  • Pass expectedSigner (the fingerprint you pinned when you paired the device). Without it the keys inside the log itself are believed, and a forger with the key writes their own.
  • A witness only knows what it was told. A log written while nobody was connected, or whose watchers were all wiped, can be cut off unnoticed. result.Witnesses tells you how many compared, and 0 means nothing was compared.
  • A witness remembers up to 16 logs per device and ignores anything that isn't a head from that device.
  • The device itself (its identity and its key) could still rewrite its own log from the start, but the devices that saw it will say so.
